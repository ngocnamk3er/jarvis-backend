# PDFs and images

Four tools do the reading on the server (bash cannot see a picture or a scanned page); `check_pdf` and `read_pdf` are loaded on demand, so first call `tool_search` with `select:check_pdf,read_pdf` (`view_image`, `ocr_image` and `draw_boxes` are always available). The sandbox's own libraries (pillow, pypdf, pdfplumber...) are for processing and making files, not for looking at them.

## A PDF
1. A file the user attached to their message is already in your working directory, under the name in the `<attachments>` block at the end of the message: use it as it is, do not `workspace_copy_to_sandbox` it (that only finds files in the user's file workspace, and says "not found" for an attachment). A file in the workspace is copied in with `workspace_copy_to_sandbox`; `workspace_read_file` also works there and is enough when you only need the words.
2. `check_pdf(path)` says, page by page, whether a page has real text, is a scan (only a picture), or has unreadable text. Do this before choosing how to read; the file name never tells you.
3. Text pages: `read_pdf(path)` writes the text to a `.txt` beside the PDF, one `=== page N ===` block per page, and gives you a short preview. Do not try to print the whole file. Find the part you need with `grep -n "word" file.txt`, then read that page with `sed -n '/=== page 12 ===/,/=== page 13 ===/p' file.txt`.
4. Scanned pages: `view_image(path, pages=[N])` shows you the page. At most 5 pages per call, so first narrow down which pages matter (a table of contents, the text pages around it, `workspace_search_files` if the file is in the workspace). It needs a vision-capable model; if the call says the model cannot see images, tell the user and suggest switching.
5. A long document: work in ranges. Answer from the pages you read, say which pages they were, and say which pages you did not read.

## An image
If the user attached it to the message it is already in your working directory (do not `workspace_copy_to_sandbox` it); if it is in their workspace, `workspace_copy_to_sandbox` it first. Then `view_image(path)`. The picture stays attached on later turns (the newest few, within a size limit), so a follow-up can be answered from it; if many images have been opened since, open it again. For exact numbers or colours, compute them in bash instead of judging by eye.

## Marking, boxing or locating things on an image
Never write pixel coordinates yourself: a model that can see a picture estimates positions tens of pixels off, and the boxes land on the wrong text. And never take the VALUES you report from OCR: it drops diacritics and loses digits. Read them with your own eyes, and use OCR only for positions. In order:
1. `view_image(path)`: read what the fields say. These are the values you give the user, quoted as printed (do not expand an abbreviation, do not complete a word that is cut off).
2. `ocr_image(path)`: where the text sits. It reads Vietnamese and English by default; for another language pass `lang` ("jpn", "chi_sim", "kor", "rus", "tha", "ara", "fra"...; one script family at a time). If the text comes out as noise or in the wrong script, read it again with the right `lang`. Text outside tables comes as lines, `L<id> [x0,y0,x1,y1] text`. A ruled table is taken out first and read cell by cell (reading across a table glues a row's cells into one line and mixes up the columns), so it comes back on its own: `Table T1`, rows `R1:`, `R2:`... with each cell as `C<n> 'text'`, and each table is also saved as a CSV file beside the image. Take a row's cells from the table, never from the lines.
3. `draw_boxes(path, items)` with, for each field to mark: a `label` (the field's NAME only, e.g. "Invoice number"), where it is (`lines`: line ids, and/or `cells`: `T1.R3.C2` one cell, `T1.R3` a row, `T1.C2` a column, `T1` the whole table), `text` with the VALUE as you read it (so the box sits on the value and not on the whole "key: value" line) and `key` with the field's printed name as it appears on the picture ("Invoice No.:"). The value and the key each get a box of their own, in the same colour (heavy on the value, light on the key), so give `key` for every field that has a printed name; if the key is not found on the picture the reply says so and only the value is boxed. Diacritics and OCR slips in `text` and `key` do not matter. There is no argument for coordinates by design, and it refuses an image that has not been through `ocr_image`.
It saves a new image of the same size (no legend or numbers: the key's own box says what the value is) and a `.json` of every box (label, value box, key box, what OCR read there), and shows it to the user under the step by itself, so do not `present_file` it. **To mark a PDF**, work one page at a time: `view_image("doc.pdf", pages=[N])` to read the page, `ocr_image("doc.pdf", page=N)` (it renders the page to `doc.pN.png` and tells you so), then `draw_boxes("doc.pN.png", ...)` with that png: it also saves `doc_boxes.pdf`, the whole PDF with your boxes over the pages you marked, and marking another page adds to it; `draw_boxes` shows `doc_boxes.pdf` to the user itself too. Find which page holds the thing first (`read_pdf` / `check_pdf`) instead of OCR-ing every page. For a table, give the user its rows as a table (the CSV file has them), each value under its own column.
Anything the reply lists as "not drawn" could not be placed: tell the user which, do not drop them silently. If the user asked for several things (boxes and a key-value list), do all of them, or say plainly which part you left out. Do not spend more than a couple of rounds adjusting the picture.

## Reporting
Name the page numbers your answer comes from. If a page was a scan you could not look at, say so rather than leaving it out silently.
